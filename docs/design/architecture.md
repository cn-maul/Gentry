# Gentry 系统架构

本文描述 Gentry 的整体系统架构、模块划分、数据流和设计决策。

## 系统概览

Gentry 是一个可自托管的网页新内容监控系统，采用 Go 后端 + React 前端的经典架构，最终打包为单二进制文件部署。系统是**纯规则驱动**的：内容识别完全依赖用户保存的扫描规则（数据库模板或外部规则文件），没有内置的启发式猜测。

```
┌─────────────────────────────────────────────────────────────────┐
│                        Gentry 单二进制                           │
├─────────────────────────────────────────────────────────────────┤
│  ┌─────────────┐  ┌─────────────┐  ┌─────────────────────────┐  │
│  │   Web 层    │  │  监控核心层  │  │       通知层            │  │
│  │  (Gin)      │  │ (Monitor)   │  │      (Notify)           │  │
│  ├─────────────┤  ├─────────────┤  ├─────────────────────────┤  │
│  │ HTTP 路由   │  │ Monitor     │  │ PushPlus                │  │
│  │ 中间件      │  │ Manager     │  │ Webhook                 │  │
│  │ API 处理器  │  │ Scanner     │  │ Server酱                │  │
│  │ 静态资源    │  │ Extractor   │  │ Bark                    │  │
│  └─────────────┘  └─────────────┘  └─────────────────────────┘  │
│  ┌─────────────┐  ┌─────────────┐  ┌─────────────────────────┐  │
│  │  抓取层     │  │   数据层    │  │     前端 (嵌入)         │  │
│  │ (Fetcher)   │  │ (Database)  │  │    (React + Vite)       │  │
│  ├─────────────┤  ├─────────────┤  ├─────────────────────────┤  │
│  │ HTTP 客户端 │  │ SQLite      │  │ 仪表盘                  │  │
│  │ 请求头控制  │  │ GORM        │  │ 监控管理                │  │
│  │ 上下文支持  │  │ 自动迁移    │  │ 高级规则 / 推送管理     │  │
│  └─────────────┘  └─────────────┘  └─────────────────────────┘  │
└─────────────────────────────────────────────────────────────────┘
```

## 模块职责

### 1. 入口层 (`main.go`)

应用入口，负责服务生命周期管理：

- 初始化数据库连接（含旧版价格监控站点的一次性清理迁移）
- 加载系统设置（推送开关等）
- 初始化外部扫描规则文件（`SCAN_RULES_FILE` 环境变量）
- 从数据库加载并启动活跃监控器
- 启动数据保留清理任务
- 启动 Web 服务
- 处理系统信号，优雅关闭

### 2. Web 层 (`web/`)

基于 Gin 框架的 HTTP 服务：

| 文件 | 职责 |
|------|------|
| `server.go` | HTTP 服务器创建、启动、优雅关闭 |
| `routes.go` | 路由注册（按领域分组）、中间件配置 |
| `payloads.go` | 请求/响应 DTO、字段互转与检测指纹 |
| `respond.go` | 统一响应构造与绑定辅助 |
| `monitors.go` | 监控 CRUD、启停、手动检查、配置校验 |
| `updates.go` | 更新历史分页查询、标记已推送/已读 |
| `scanrules.go` | 扫描规则 CRUD、导入导出、快速创建、规则测试 |
| `accounts.go` | 推送账户 CRUD、敏感配置脱敏回填、推送开关 |
| `system.go` | 健康检查、统计、分组 |
| `ai.go` | AI 模型接入设置与 AI 规则提取 |
| `update.go` | 自动升级逻辑 |
| `security.go` | 认证中间件、出站 URL 安全校验 |
| `embed.go` | 前端 SPA 静态资源嵌入与回退 |
| `types.go` | API 响应类型定义 |

**路由分组：**
- `/api/v1/monitors` - 监控器管理（含 `check`/`validate`/`preview`）
- `/api/settings/*` - 系统设置（推送账户、扫描规则等）
- `/api/version`, `/api/update/*` - 版本和升级

### 3. 监控核心层 (`monitor/`)

系统的核心，只有一条检查路径：

| 文件 | 职责 |
|------|------|
| `monitor.go` | 监控器主体：检查循环、提取比对、更新记录、同步通知 |
| `manager.go` | 监控器注册、启停、原子替换管理 |
| `scanner.go` | 规则驱动扫描：遍历命中规则生成监控配置候选 |
| `scanner_rules.go` | 扫描规则库：scope 匹配、数据库模板、外部规则文件 |
| `extractor.go` | CSS 选择器字段提取（含旧配置修复启发式） |
| `source.go` | 数据源配置解析（HTML / JSON API、动态页面变量） |
| `definition.go` | 监控定义的规范化与校验 |
| `validation.go` | 只读提取验证（配置测试） |

**唯一检查路径：**

```
Monitor.CheckNow() → extractSiteResults() → compareResults() → saveResults()
                                       ↓
                              有新条目 → sendCombinedNotification()（同步推送）
```

### 4. 抓取层 (`fetcher/`)

HTTP 请求封装：

| 文件 | 职责 |
|------|------|
| `fetcher.go` | HTTP 客户端、请求执行 |
| `config.go` | 配置结构定义 |
| `options.go` | 函数式选项模式 |

**安全特性：**
- 请求头白名单控制（仅允许 Accept、Accept-Language、Referer、X-Requested-With）
- 响应大小限制（10MB）
- 上下文支持（超时/取消传递）

### 5. 通知层 (`notify/`)

多渠道通知实现（同步发送，随检查循环执行）：

| 文件 | 职责 |
|------|------|
| `interface.go` | Notifier 接口定义 |
| `manager.go` | 全局推送开关管理 |
| `pushplus.go` / `webhook.go` / `serverchan.go` / `bark.go` | 渠道实现 |
| `account.go` | 账户配置管理 |
| `registry.go` | 服务注册表 |

### 6. 数据层 (`database/`)

SQLite 数据持久化：

| 文件 | 职责 |
|------|------|
| `db.go` | 数据库初始化、连接配置、旧版数据迁移 |
| `models.go` | GORM 模型定义 |
| `retention.go` | 数据保留清理（update_records） |
| `site_repository.go` | 站点数据访问 |
| `scan_rule_repository.go` | 扫描规则数据访问 |

## 数据模型

### 核心实体关系

```
┌──────────────┐     ┌──────────────────┐
│    Site      │────<│   SiteField      │
│  (监控站点)   │     │  (提取字段配置)   │
└──────────────┘     └──────────────────┘
       │ 1:N                  ┌─────────────────────┐
       ▼                      │  ScanRuleTemplate   │
┌──────────────────┐          │   (扫描规则模板)     │
│  UpdateRecord    │          └─────────────────────┘
│  (更新历史)       │                    │ 1:N
└──────────────────┘                    ▼
                              ┌─────────────────────┐
                              │   ScanRuleField     │
                              │   (规则字段配置)     │
                              └─────────────────────┘
```

### 关键模型说明

| 模型 | 用途 | 关键字段 |
|------|------|----------|
| `Site` | 监控站点配置 | Container, Item, FetchConfig, ConfigVersion, BaselineStatus |
| `SiteField` | 提取字段定义 | Name, Selector, Type, Attr, Transform |
| `UpdateRecord` | 更新历史（也是去重基准） | Title, URL, Notified, IsRead |
| `ScanRuleTemplate` | 扫描规则 | ScopeType, MatchHost, MatchPath, Priority |
| `ScanRuleField` | 规则字段定义 | Name, Selector, Type, Attr, Transform |
| `NotificationAccount` | 推送账户 | Name, Service, ConfigJSON |

## 核心数据流

### 1. 定时检查流程

```
┌─────────┐    ┌─────────┐    ┌──────────┐    ┌──────────┐    ┌─────────┐
│ Ticker  │───>│ Fetcher │───>│Extractor │───>│ compare  │───>│ 更新记录 │
│ (定时器) │    │ (抓取)  │    │ (提取)   │    │ (比对去重)│    │ + 推送  │
└─────────┘    └─────────┘    └──────────┘    └──────────┘    └─────────┘
```

条目按「标题 + 链接」作为唯一键：`update_records` 表既是去重基准（已见过的组合不再通知），也是更新历史。首次成功抓取只建立基线，不推送页面已有内容。

### 2. 规则扫描流程（创建监控时的内容识别）

```
┌─────────┐    ┌───────────────────────────────────────────────┐
│ 用户输入 │───>│              规则扫描器                        │
│   URL   │    │  ┌──────────────┐      ┌───────────────────┐ │
└─────────┘    │  │ JSON API 规则 │ 或   │ HTML 规则遍历      │ │
               │  │ (直接请求接口) │      │ (命中 URL 的模板)  │ │
               │  └──────────────┘      └───────────────────┘ │
               └───────────────────────────────────────────────┘
                                        │
                                        ▼
                          ┌─────────────────────────┐
                          │ 候选列表（按规则优先级）  │
                          │ 含样本条目与监控配置      │
                          └─────────────────────────┘
```

无规则命中时返回空列表，由前端提示用户先创建规则。规则本身在「高级规则」页手动创建（填写选择器/JSON 路径 + 测试提取）、从监控表单另存、或批量导入。

## 并发模型

### 锁机制

| 锁 | 位置 | 用途 |
|----|------|------|
| `monitorsLock` | `manager.go` | 保护监控器注册表 |
| `siteLock` | `Monitor` | 保护站点配置快照 |
| `statusLock` | `Monitor` | 保护状态信息 |
| `runLock` | `Monitor` | 防止重复启动检查循环 |
| `cancelLock` | `Monitor` | 保护检查取消函数 |
| `checkGate` | `Monitor` | 串行化检查（channel 信号量） |
| `settingsLock` | `notify/manager.go` | 保护推送开关 |

### 并发控制策略

1. **监控循环串行化**：`checkGate` channel 确保同一时间只有一个检查在执行
2. **数据库写入串行化**：SQLite 单连接 + WAL 模式 + busy_timeout
3. **优雅关闭**：`sync.Once` + context 超时

## 配置版本机制

当监控配置（URL、选择器、字段、数据源）发生变化时：

1. Web 层计算配置语义指纹（`computeDetectionFingerprint`）
2. 指纹不同则 `ConfigVersion` 递增、`BaselineStatus` 设为 `needs_baseline`
3. 下次检查时重建基线（首查不通知）

这确保了配置变更不会导致误报。名称、检查间隔和通知账户等非语义修改不触发基线重建。

## 错误处理策略

| 场景 | 策略 |
|------|------|
| 抓取失败 | 记录错误，保留上次基线，下次重试 |
| 通知发送失败 | 记录日志，更新记录保留未推送状态，可在界面标记 |

## 设计决策

### 为什么用 SQLite？

- 单二进制部署，无需外部数据库
- 数据量适中（监控配置 + 更新历史 + 规则）
- WAL 模式支持读写并发
- 便于备份（单文件复制）

### 为什么扫描是纯规则驱动？

- 同一站点每次识别结果稳定一致，不依赖启发式猜测
- 规则可测试、可导入导出、可跨实例复用
- 删除了约 800 行启发式策略与评分合并代码，扫描器行为完全可预测
- 未命中规则时明确提示用户创建规则，而不是给出质量未知的猜测候选

### 为什么通知是同步发送？

检查循环本身串行执行，单次通知耗时可控；发送失败只影响当次推送，更新记录仍保留未推送状态供用户查看。曾经的异步投递队列只服务于已移除的价格事件语义，随之删除。

## 扩展点

### 添加新的通知渠道

1. 实现 `Notifier` 接口
2. 在 `registry.go` 中注册服务类型
3. 添加账户配置结构

### 添加新的数据源模式

1. 在 `source.go` 的 `FetchConfig` 中添加模式
2. 在 `extractSiteResults` 中实现抓取与解析分支
