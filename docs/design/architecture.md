# Gentry 系统架构

本文描述 Gentry 的整体系统架构、模块划分、数据流和设计决策。

## 系统概览

Gentry 是一个可自托管的网页变化监控系统，采用 Go 后端 + Vue 3 前端的经典架构，最终打包为单二进制文件部署。

```
┌─────────────────────────────────────────────────────────────────┐
│                        Gentry 单二进制                           │
├─────────────────────────────────────────────────────────────────┤
│  ┌─────────────┐  ┌─────────────┐  ┌─────────────────────────┐  │
│  │   Web 层    │  │  监控核心层  │  │       通知层            │  │
│  │  (Gin)      │  │  (Monitor)  │  │      (Notify)           │  │
│  ├─────────────┤  ├─────────────┤  ├─────────────────────────┤  │
│  │ HTTP 路由   │  │ Engine      │  │ PushPlus                │  │
│  │ 中间件      │  │ Monitor     │  │ Webhook                 │  │
│  │ API 处理器  │  │ Detector    │  │ Server酱                │  │
│  │ 静态资源    │  │ Scanner     │  │ Bark                    │  │
│  └─────────────┘  └─────────────┘  └─────────────────────────┘  │
│  ┌─────────────┐  ┌─────────────┐  ┌─────────────────────────┐  │
│  │  抓取层     │  │   数据层    │  │     前端 (嵌入)         │  │
│  │ (Fetcher)   │  │ (Database)  │  │    (Vue 3 + Vite)       │  │
│  ├─────────────┤  ├─────────────┤  ├─────────────────────────┤  │
│  │ HTTP 客户端 │  │ SQLite      │  │ 仪表盘                  │  │
│  │ 请求头控制  │  │ GORM        │  │ 监控管理                │  │
│  │ 上下文支持  │  │ 自动迁移    │  │ 推送配置                │  │
│  └─────────────┘  └─────────────┘  └─────────────────────────┘  │
└─────────────────────────────────────────────────────────────────┘
```

## 模块职责

### 1. 入口层 (`main.go`)

应用入口，负责服务生命周期管理：

- 初始化数据库连接
- 加载系统设置（推送开关等）
- 初始化扫描规则
- 从数据库加载并启动活跃监控器
- 启动数据保留清理任务
- 启动投递服务
- 启动 Web 服务
- 处理系统信号，优雅关闭

### 2. Web 层 (`web/`)

基于 Gin 框架的 HTTP 服务：

| 文件 | 职责 |
|------|------|
| `server.go` | HTTP 服务器创建、启动、优雅关闭 |
| `routes.go` | 路由注册、中间件配置 |
| `operations.go` | 监控 CRUD、启停、检查等业务处理器 |
| `update.go` | 自动升级逻辑 |
| `security.go` | 认证中间件 |
| `types.go` | API 响应类型定义 |

**路由分组：**
- `/api/v1/monitors` - 监控器管理
- `/api/settings/*` - 系统设置（推送账户、扫描规则等）
- `/api/version`, `/api/update/*` - 版本和升级

### 3. 监控核心层 (`monitor/`)

系统的核心，负责网页监控的整个生命周期：

| 文件 | 职责 |
|------|------|
| `engine.go` | 新版检查引擎，编排完整检查流程 |
| `monitor.go` | 监控器主体，管理检查循环和状态 |
| `manager.go` | 监控器注册、启停、替换管理 |
| `detector.go` | 检测器接口和规则验证 |
| `detectors.go` | PresenceDetector、FieldTransitionDetector 实现 |
| `scanner.go` | 智能预扫描，自动发现页面结构 |
| `extractor.go` | CSS 选择器字段提取 |
| `normalize.go` | 字段值规范化、类型转换 |
| `scanner_rules.go` | 扫描规则库管理 |
| `delivery_service.go` | 投递队列服务 |
| `source.go` | 数据源配置解析 |
| `types.go` | 核心类型定义 |

**两种检查路径：**

```
旧版路径 (presence 策略):
Monitor.checkForUpdatesContext() → extractSiteResults() → compareResults()

新版路径 (presence/field_transition 策略):
Engine.CheckOnce() → observe() → detector.Evaluate() → PersistEvaluation()
```

### 4. 抓取层 (`fetcher/`)

HTTP 请求封装：

| 文件 | 职责 |
|------|------|
| `fetcher.go` | HTTP 客户端、请求执行 |
| `config.go` | 配置结构定义 |
| `options.go` | 函数式选项模式 |

**安全特性：**
- 请求头白名单控制（仅允许 Accept、Accept-Language、Referer、X-Requested-With）
- 响应大小限制（10MB）
- 上下文支持（超时/取消传递）

### 5. 通知层 (`notify/`)

多渠道通知实现：

| 文件 | 职责 |
|------|------|
| `interface.go` | Notifier 接口定义 |
| `manager.go` | 全局推送开关管理 |
| `pushplus.go` | PushPlus 实现 |
| `webhook.go` | Webhook 实现 |
| `serverchan.go` | Server酱实现 |
| `bark.go` | Bark 实现 |
| `account.go` | 账户配置管理 |
| `registry.go` | 服务注册表 |

### 6. 数据层 (`database/`)

SQLite 数据持久化：

| 文件 | 职责 |
|------|------|
| `db.go` | 数据库初始化、连接配置 |
| `models.go` | GORM 模型定义 |
| `retention.go` | 数据保留清理 |
| `site_repository.go` | 站点数据访问 |
| `scan_rule_repository.go` | 扫描规则数据访问 |

## 数据模型

### 核心实体关系

```
┌──────────────┐     ┌──────────────────┐     ┌─────────────────────┐
│    Site      │────<│   SiteField      │     │  ScanRuleTemplate   │
│  (监控站点)   │     │  (提取字段配置)   │     │   (扫描规则模板)     │
└──────────────┘     └──────────────────┘     └─────────────────────┘
       │                                            │
       │ 1:N                                        │ 1:N
       ▼                                            ▼
┌──────────────────┐                        ┌─────────────────────┐
│ MonitorSnapshot  │                        │   ScanRuleField     │
│  (条目快照)       │                        │   (规则字段配置)     │
└──────────────────┘                        └─────────────────────┘
       │
       │ 1:N
       ▼
┌──────────────────┐     ┌─────────────────────┐
│  MonitorEvent    │────<│NotificationDelivery │
│  (变化事件)       │     │   (投递任务)         │
└──────────────────┘     └─────────────────────┘
                              │
                              │ N:1
                              ▼
                        ┌─────────────────────┐
                        │NotificationAccount  │
                        │   (推送账户)         │
                        └─────────────────────┘
```

### 关键模型说明

| 模型 | 用途 | 关键字段 |
|------|------|----------|
| `Site` | 监控站点配置 | StrategyType, StrategyConfig, ConfigVersion, BaselineStatus |
| `SiteField` | 提取字段定义 | Name, Selector, Type, Attr, Transform |
| `MonitorSnapshot` | 条目当前状态 | ItemKey, PayloadJSON, Fingerprint, PriceMinor, Currency |
| `MonitorEvent` | 变化事件 | EventType, ItemKey, DedupeKey, DeliveryStatus |
| `NotificationDelivery` | 投递任务 | Status, Attempts, LeaseUntil, NextAttemptAt |
| `ScanRuleTemplate` | 扫描规则 | ScopeType, MatchHost, MatchPath, Priority |

## 并发模型

### 锁机制

| 锁 | 位置 | 用途 |
|----|------|------|
| `monitorsLock` | `manager.go` | 保护监控器注册表 |
| `siteLock` | `Monitor` | 保护站点配置快照 |
| `statusLock` | `Monitor` | 保护状态信息 |
| `runLock` | `Monitor` | 防止重复启动检查循环 |
| `cancelLock` | `Monitor` | 保护检查取消函数 |
| `checkGate` | `Monitor` | 串行化检查（channel 信号量） |
| `settingsLock` | `notify/manager.go` | 保护推送开关 |

### 并发控制策略

1. **监控循环串行化**：`checkGate` channel 确保同一时间只有一个检查在执行
2. **数据库写入串行化**：SQLite 单连接 + WAL 模式 + busy_timeout
3. **投递任务原子 Claim**：SQL 条件更新防止重复领取
4. **优雅关闭**：`sync.Once` + context 超时

## 配置版本机制

当监控配置（选择器、字段、策略）发生变化时：

1. `ConfigVersion` 递增
2. `BaselineStatus` 设为 `needs_baseline`
3. 下次检查时重建基线
4. 快照的 `DefinitionVersion` 与配置版本关联

这确保了配置变更不会导致误报。

## 错误处理策略

| 场景 | 策略 |
|------|------|
| 抓取失败 | 记录错误，保留上次基线，下次重试 |
| 价格解析失败 | 保留上次有效价格，不覆盖基线 |
| 币种变化 | 不跨币种比较，保留旧基线 |
| 通知发送失败 | 指数退避重试（5min → 24h），10 次后标记 dead |
| 投递任务超时 | 回收过期 sending 任务，重新投递 |
| 检查 panic | recover 记录，不影响监控循环 |

## 设计决策

### 为什么用 SQLite？

- 单二进制部署，无需外部数据库
- 数据量适中（监控配置 + 快照 + 事件）
- WAL 模式支持读写并发
- 便于备份（单文件复制）

### 为什么有两种检查路径？

旧版 `Monitor.checkForUpdatesContext` 用于兼容已有的 `presence` 监控，新版 `Engine` 统一处理所有策略。未来计划统一到 Engine。

### 为什么投递要异步？

- 通知发送不应阻塞监控循环
- 支持失败重试和指数退避
- 多个账户可以并行发送
- 投递状态可追踪
